# bn reference — reading

Read-command catalog for the `bn` skill. Open when surveying/decompiling. See `../SKILL.md` for the map.
## 4. Read flow

```bash
bn target info
bn target list [--format json]                       # open targets + their selectors; `selector` is what -t takes
bn function list [--count] [--min-address 0x401000 --max-address 0x40ffff]
bn function list [--sort {address|size|name}] [--reverse] [--min-size 64] [--demangle]
bn function list [--named | --unnamed]               # meaningful names vs BN's auto sub_* (import thunks in neither)
bn function search attachment [--count]              # --count here = MATCHES, not the whole-binary total
bn function search --regex 'attach|detach|follow'
bn function search <q> [--sort … --reverse --min-size N --demangle]
bn function info <fn> [--verbose] [--blocks]         # --blocks: basic-block address ranges + edges
bn decompile <fn> [--addresses] [--lines 40:80] [--force-analysis] [--include-annotations]
bn il <fn> [--view {hlil|mlil|llil}] [--ssa]          # --level is an accepted alias for --view
bn disasm <fn> [--lines 40:80 | --count 20]
bn disasm <addr> --linear [N]                        # up to N (default 32) units: one physical instruction or one undecodable .byte byte
bn xrefs <fn-or-addr> [--limit 20]
bn xrefs --field <Struct.field>
bn callsites <callee> --within <fn>
bn callsites <callee> --within-file <path>
bn evidence function <fn> [--context 2]              # per-call ABI args (LLIL/MLIL/HLIL + raw disasm) + thunk detection
bn evidence xrefs <fn-or-addr> [--limit N]           # inbound refs annotated with section/segment/symbol/disasm
bn evidence table <addr> [--entries N] [--stride N]  # interpret memory as a pointer/vtable table (Thumb-normalized)
bn evidence table <addr> --record-size N --ptr-fields o1,o2  # mixed-record mode: scalar + pointer fields per record
bn evidence table <addr> --record-size N --field cmd:u32@0 --field name:char[16]@8   # typed scalar/string fields
bn evidence calls <reg-fn> --arg-struct N --field type:u8@2 --field cb:ptr@16  # stack-descriptor fields per callsite
bn evidence message <type-string> [--limit N]        # protobuf/RTTI type-name -> xrefs -> nearby metadata table windows
bn evidence init [--limit N]                         # .init_array/.ctors constructor-pointer summary
bn evidence orient                                   # one-shot triage digest under a single read lock: target + analysis state, imports, strings sample, sections
bn evidence surface                                  # hidden code surface: init/ctor + vtable/dispatch tables + data-referenced code BN missed
bn evidence virtual-call --at <addr> [--providers <selector>]   # resolve an imported abstract/interface virtual call to the provider's vtable method
bn trace <fn> <addr> [--arg N] [--interprocedural]   # backward SSA slice: trace where a call argument originates
bn dataflow defuse <fn> --var <name|local_id|name#version>   # SSA def site + use sites of one variable
bn dataflow callgraph <fn> [--direction {callees|callers|both}]   # resolved edges; indirect targets via value-set
bn dataflow values <fn> --at 0x401234                # value-set (possible values) at an instruction
bn taint models [--role {source|sink|propagator}] [--class overflow_len] [--present]   # known sources/sinks; --present needs a target
bn taint forward -f <fn> --source param:0 [--sink-class recv_overflow]   # untrusted data source→sink across calls (methodology → the `bn-vr` skill)
bn taint backward -f <fn> --sink arg:memcpy:2         # slice a sink's args back to their origin (`bounded: true` = provably bounded)
bn function cfg <fn> [--view {asm|mlil|hlil}]        # basic-block graph: blocks, their instructions, and the typed edges between them
bn function structured-il <fn>                       # flat per-instruction list: op plus vars_read/vars_written, no block partitioning
bn proto get <fn>
bn local list <fn>
bn data vars --start <addr> --end <addr>             # typed data variables in an address window (the window is mandatory)
bn data symbols [--limit N]                          # every named DataSymbol, including internals `bn exports` omits
bn read 0x... --length N [--encoding {hex|bytes}]   # address is positional; --address 0x... is an accepted alias
bn function create <address> [--preview]
bn types [--query <q>]
bn types show <name>
bn struct show <name>
bn class list [--all] [--no-stl] [--query <substr>]   # C++ classes from demangled symbols + RTTI
bn class show <Name>                                  # one class: methods, vtable, size, bases, instances
bn strings [--query <q>] [--regex] [--min-length 5] [--section .rodata] [--no-crt]
bn imports
bn exports [--count]                                 # public exported symbols (contrast `imports`)
bn go functions [--summary | --count]                # recover Go names from .gopclntab (then `bn go rename`, a mutation)
bn sections [--query <q>]
bn tag list [--type Bookmarks --query <substr>]      # tags at all scopes; `--type Bookmarks` is the bookmarks tag
bn tag get 0x401000 | --function <fn>                # tags at one address, or the whole-function tags
bn tag types                                         # tag types (built-in + custom)
bn comment list [--query <q>] [--scope {all|address|function}]   # `all` (default) includes function docs
bn comment get   --address 0x... | --function <fn>
```

Notes:

- `bn function search` is case-insensitive substring; add `--regex` for regular expressions. A query with unescaped regex metacharacters (`|()[]{}*+?^$\`) that matches **nothing literally** is auto-retried as a regex, so `bn function search 'Parse|Process|Decode'` finds the alternation instead of a confident (misleading) `none`; the switch is disclosed on stderr and, in `--format json`, with a top-level `"regex_fallback": true` (add `--exact` to force a literal match). `function list` and `function search` both accept `--min-address` / `--max-address`. Both also accept `--count`, which returns just the total (`function list --count` = whole-binary function count for fast sizing; `function search <q> --count` = number of matches for a query) instead of the listing.
- **Duplicate function start addresses are disclosed in text, not only in JSON.** Binary Ninja can hold two Function records for one start address with conflicting sizes (#757). `function list` and `function search` collapse the same population, everything `--min-address`/`--max-address` left, before the query matches anything; what happens there depends on whether the records can be RANKED. **Ranked** (every extent readable): the address answers with ONE row carrying the larger extent, the rest are gone from both commands, and naming it returns nothing. **Unranked** (any extent unreadable): no record is chosen, so ALL of that address's records stay in the answer, however many there are, and naming any of them returns it. A record BN did size still reports `size_known: true` there, which means BN stated a size, not "this size won". Each returned row of a duplicated start therefore carries `duplicate_start`: `"collapsed"` when this record won on extent, `"unresolved"` when nothing was ranked here — so a `--sort size` page that splits the group apart is still self-describing. The counts are `duplicate_starts_collapsed` / `duplicate_starts_unresolved`, printed in text as a `// duplicate starts` line: last on the `function list` listing and on `--count`, and directly under the function count on `target info` and on `evidence orient`, whose counts are post-collapse too. **Scope, one rule:** both counts are taken over the whole filtered answer `total` reports, everything `--min-size`, `--named` and the query left, and are NOT affected by `--offset`/`--limit`, so a page can disclose an address none of its rows holds, which is why the note names the total it counted against and why the rows carry their own label. They count ADDRESSES, not dropped records: a filter that removes every record of an address removes its count with it, while an address that keeps even one record stays counted, so `duplicate_starts_unresolved: 1` beside `total: 1` is the expected shape, not a missing row. Both keys exist only when non-zero, so a clean view prints nothing extra.
- **`bn evidence orient` emits the annotation block ONCE**, at the payload's top level (`existing_annotations`); it is not repeated under `target`. `target info` publishes the same block under its own top-level key.
- **Source/sink name surveys: prefer `--exact` or an anchored `--regex`.** A plain **substring** search for a short API name pulls in unrelated identifiers that merely contain it — `bind` matches `RebindConfig`/`unbind_user`, `recv` matches `recv_queue_drain`, `ftp` matches `tftpSendFile`, `system` matches `subsystem_init`. `--word` (`\b<query>\b`) rejects those identifier-token fusions, but it still can't force an exact *family* and admits decorated/clone variants that survive a word boundary (`popen.cold`, `recv.constprop`, `.part`). For a **known** API name use `bn function search bind --exact`; for a **family** use an anchored alternation `bn function search --regex '^(bind|recv|recvfrom|listen|accept)$'`. Treat substring search as **DISCOVERY only**, then confirm every hit against `bn imports` and the actual call target (`bn xrefs <hit>` / `bn evidence function`) before reporting it as a source or sink — a name match is not a sink.
- `bn xrefs` accepts a function name *or* a hex/decimal address. Text groups refs by caller (`code refs: 12 sites across 4 functions`); JSON adds `caller_function: {address, name}` so an `xrefs → --within-file` pipeline survives duplicate symbol names. Use `bn xrefs` for inbound references; reach for `bn callsites` when you need exact return-address recovery and local context.
- `bn decompile` renders Binary Ninja Pseudo C and redacts inherited global address, function-local address, and function-doc annotation bodies by default in both text and JSON. Redaction matches complete stored body lines in standalone or inline/trailing `//` comments, ignoring surrounding whitespace; code, quoted/escaped literals, address gutters, and unrelated comments are preserved. Block comments and differently rendered bodies are not scrubbed. The payload reports an annotation count; its legacy `comments` map contains global address comments only and is empty by default. `--include-annotations` is the explicit opt-in after a contamination decision and retains the rendered bodies from all three stores. Add `--addresses` when an address gutter is needed.
- **Skipped (oversize) functions.** Binary Ninja skips analysis on functions that exceed its size/time limits and renders only a stub ("…taking too long to analyze… Loading…"). `bn decompile` detects this (`func.analysis_skipped`) and appends a `warning:` (and sets `analysis_skipped: true` in JSON) so you never mistake a stub for a real body. Pass `--force-analysis` to override the skip and reanalyze just that function before decompiling — it returns the full body and sets `analysis_forced: true`. It can be slow on very large functions and takes the **write lock** (it mutates analysis state), so avoid it on a bridge other agents are actively reading.
- **Width-sensitive reads — trust `bn disasm`, not the decompiler.** Pseudo C and HLIL share the same analysis and can hide the real access width. A byte compare (`cmp al, ...`) renders as a full-width equality, and a `zx.d` on a dereference does **not** imply a 4-byte load (it can be a 1-byte load zero-extended to 4). When the exact comparison width or memory-read size matters (off-by-one, OOB, signedness bugs), treat `bn disasm <fn>` as authoritative and confirm the operand size there before reasoning about the bug.
- `bn disasm <function> --lines N:M` is a 1-indexed slice of the bridge's canonical address-ordered function listing; `--count N` selects its first N rows. Each decoded physical instruction, including the IT and each covered Thumb instruction, occupies its own row. Fallback `.byte` rows can name multiple undecodable bytes; unreadable addresses have an explicit diagnostic row. These switches count listing rows, not bytes or addresses. Invalid/out-of-range windows fail loudly.
- For instruction adjacency outside recovered function blocks, use `bn disasm <addr> --linear N`. N and JSON `instruction_count` count emitted units: one decoded physical instruction (variable width), or one undecodable byte shown as `.byte 0xNN`. IT-covered instructions each consume their own unit; a `.byte` unit is not a successfully decoded instruction. The walk stops at an unmapped tail and discloses the existing request cap.
- `bn class` is the **C++ object-model lens** (#205): a correlation layer over data BN already recovers (demangled symbols, RTTI data symbols, vtables). `bn class list` clusters the binary's functions by demangled class and shows method count, vtable presence, and a confidence tag (`rtti` = has vtable/typeinfo, `ctor` = has a ctor/dtor, `name-only` = could be a namespace); it defaults to `rtti`+`ctor`-confirmed classes, with `--all` to include `name-only` clusters, `--query` to filter, and `--no-stl` to fold out standard-library / ABI-runtime classes (`std::`, `__gnu_cxx::`, `__cxxabiv1::`, reserved-id internals) so domain classes surface (it reports how many it hid). `bn class show <Name>` resolves one class (exact, or by leaf name across namespaces — ambiguous names list every match) and reports: methods grouped ctor/dtor + non-virtual members; the vtable layout (Itanium header-skipped, with `__cxa_pure_virtual`, external/cross-module, `<null>`, and unnamed-`sub_*` slots each marked); object size (from a defined BN type when present); RTTI base classes (Itanium `__si`/`__vmi` decode); and instances (ctor construction sites from code xrefs + globals that store the vtable), each of them CAPPED AND SAYING SO (#822): the vtable reports `truncated`/`slots_truncated` with a nullable exact `total` (null whenever the table's end was not OBSERVED -- `truncated_reason` names why: "scan_capped" for a cap-truncated scan, "unreadable_row" when the scan stopped at an entry it could not read (a failed read is not an end), "no_local_vtable_body" when the address has no decodable local body at all; `total_lower_bound` is the validated minimum -- the listing's entries plus the proven lookahead row -- and `scan_truncated: true` marks the two stopped scans, while the reason is null once the end was observed), and the construction-site / stored-global lists cap at 128 each while reporting `construction_sites_total`/`stored_globals_total` and their `*_truncated` flags, so a prefix never reads as a total. Each `methods[]` row (including ctors/dtors) preserves its original `address` and adds `thunk: {is_candidate, reason, target, sections}` from the same detector as `evidence function`, evaluated only for the requested class matches. Text marks `thunk/veneer candidate` with the reason and either `target -> ...` (detector-supported target evidence) or `target unresolved`; a known target does not by itself confirm a thunk. A `.plt` entry is a candidate with no resolved target, even when a same-mangled `.text` method exists: both addresses remain separate, and matching names never establish a branch destination. A local forwarding target may be present with `is_candidate: false`; text discloses `local branch -> ...; not a confirmed thunk/veneer` rather than upgrading it to a thunk. Detection remains best-effort: a false candidate flag is not proof of a full implementation body. `class list`'s `thunks_suppressed` counts thunk-shaped class-name artifacts, not detected method veneers. PIE `.data.rel.ro` vtables now resolve via the same relocation-aware reader as `evidence table` (#441), including vtables whose slots interleave null / pure-virtual / cross-module entries. Best-effort gaps to know: a vtable defined in another module (its local symbol is an import/GOT slot) still shows "no slots resolved"; `operator new` object-size and per-site new/stack/global classification are not yet recovered (size falls back to a defined type; sites are reported as `ctor-call`). `--format json` carries the full record. When the count is **zero**, the result also carries `inputs` (`demangled_cxx_methods`, `rtti_typeinfo_symbols`, `rtti_vtable_symbols`) and the text prints them — zero across all three means the target genuinely has no C++ type evidence, rather than the lens having failed to cluster (#653), so you don't have to prove RTTI absence by hand with `strings --regex '_ZTV|_ZTI'`.
- `bn imports` JSON tags each entry with `kind` (`function`, `data`, `address`) and includes `library` + `raw_name`. Text marks data/address imports with `(data)` / `(address)`.
- `bn sections` exposes start/end, length, semantics, and segment-derived `r/w/x` permission flags. `--query` matches a substring of the section **name or its semantics label** (case-insensitive), so `--query code` finds executable sections (`.text` = `ReadOnlyCode`) and `--query data` finds the data sections, not just literal name matches.
- `bn strings`: `--no-crt` is a heuristic — drops single-character repetitions and strings sitting in `.text`. Combine with `--min-length` and `--section`. Add `--regex` to treat `--query` as a case-insensitive regex (use it for OR patterns like `'%s|%n|/bin/'` — plain `--query` is literal substring, so `\|` does **not** mean OR). A `--query` value that looks like a flag (e.g. `-h`) is preserved as the query, but a known sibling flag right after `--query` (e.g. `--regex`) still errors — put flags before `--query` or use `--query=<value>`. JSON is a paged `{items, total, ...}` envelope where each item is `{address, length, chars, type, value}` — the string text is in **`value`**, not `string`. Extract it with `bn strings --query foo --format json | jq -r '.items[].value'`. (A wall of `null` from `jq '.items[].string'` means the wrong field name, not "no match" — a true no-match returns an empty `items` array.)
- `bn go functions` recovers addresses from `.gopclntab`, and `defined` is satisfied by **containment**, not only by a function start — so the counters that decide whether the addresses can be trusted are `start_match_count` (`start_matches:` in the `--summary` text) against `defined` / `defined_count`: a row resolving only as an **interior PC** of some body is not evidence that the table is based correctly. The `note` is ONE string carried by text, `--summary`, the paged listing, and JSON alike, and it fires whenever most resolved rows are interior-only — including when a *single* row happens to match a start, which is exactly the rebased-table shape (one row lands on a prolog, the rest land off it). `text_start` vs `text_start_bv` is the rebase check the note names. A page carries the note above its rows, so `--offset` / `--limit` cannot hide it.
- **JSON envelope contract (#275).** Every collection-returning read emits ONE shape:
  `{"kind": <discriminator>, "items": [...], "total": N, "offset": 0, "limit": L, "returned": R, "has_more": bool}`.
  `kind` names what the items are; `items` is the data container for **every** read command, `local list` included (the old `functions`/`classes`/`code_refs`/`data_refs` keys were dropped; `local list` retains `locals` as a same-list alias for compatibility, and `xrefs` still exposes the `code_ref_count`/`data_ref_count` totals alongside `items`). Any command not in the leaf map below still answers to `.items[]`. `--count` mode returns `{"kind": <same>, "count": N, "total": N}` (no `items`). `kind` values: `functions` (list+search), `strings`, `imports`, `exports`, `sections`, `types`, `xrefs`, `field_xrefs` (`xrefs --field`), `symbol_presence` (`xrefs --any`), `callsites`, `classes`, `comments`, `pointer_table` (`evidence table`), `init_arrays` (`evidence init`), `messages` (`evidence message`), `imports_summary` (`imports --summary`, a keyed aggregate that keeps `namespaces`/`by_kind`, not a flat `items` list).
  - **`row_fields`: in-band row-key discovery.** Row schemas differ **on purpose** — `functions` key on `address`/`size`, `sections` on `start`/`end`/`length`, `callsites` nest `callee`/`containing_function` — so every collection envelope also carries `row_fields`: the list of keys a row of that collection can have. Read it instead of guessing (`bn sections --format json | jq -r '.row_fields[]'`), and note it is present on a **zero-hit** page too, which is exactly when there is no row to infer the schema from. It is attached at the bridge's dispatch boundary, so it covers every collection read (current and future) over both the CLI and native paths, and there is no separate schema catalog to drift: on a populated page the hint is the union of the declared keys and the keys the rows actually carry. In the retained kernel it is `s.last.row_fields`.
  - **Envelope tiers (so `kind`+`items` is uniform but the trailing keys vary by what the read actually does):**
    - **Paged collections** (`function list`/`search`, `strings`, `imports`, `exports`, `sections`, `types`, `callsites`, `xrefs`, `xrefs --field`, `comment list`, `class list`) carry the full paging quad `{offset, limit, returned, has_more}` and honor `--offset`/`--limit`.
    - **Unpaged / fixed-window / presence reads** carry `{kind, items, total}` but **omit the paging quad** (they return the full set or a bounded window, not offset-pages): `evidence init`, `evidence table` (`--entries N` window). `xrefs --any` is a presence sweep — `{kind, items, count, present}` (one row per probed symbol; `count`/`present` are its summary, not paging).
    - **Top-N capped:** `evidence message --limit N` returns `{kind, items, total, truncated}` — `total` is matches found, `truncated: true` means more exist beyond the cap (raise `--limit`; it is not offset-paged).
    - **Keyed aggregate:** `imports --summary` keeps `namespaces`/`by_kind` and has no `items`.
  - **Nested tables are canonical too:** a pointer table embedded inside `evidence init` (`section.table`) or `evidence message` (`metadata_table_windows[]`) is the **same** `{kind: "pointer_table", items, total, …}` shape as the standalone `evidence table` op — one `.items[]` path everywhere (#275). `evidence message` items each also retain a nested `xrefs` object (which carries `code_refs`/`data_refs` — an intentional embed, not a top-level alias).
  - **Spilled output is NOT the data (#311) — but spilling is opt-in.** With `BN_SPILL_TOKENS=<tokens>` armed, a heavy `--format json` read (e.g. `xrefs` on a 100+ caller sink) spills to disk; stdout then carries only the spill envelope `{ok, spilled: true, artifact_path, total, bytes, tokens, summary}` — there is **no `items` key**, so `jq '.items'` reads null and a 120-caller sink misreads as "0". By default nothing spills and stdout carries the data, so `.items` is real (bound the read if your wrapper truncates big payloads). **Do not key your inline-vs-artifact branch on `.spilled`.** It is an ENVELOPE field — `true` when the threshold spilled the body, `false` when `--out` wrote it to your named file — and a default payload has no envelope, hence **no `spilled` key**, so `jq '.spilled == false'` reads null there and a "is the data inline?" branch keyed on it never matches. The pointer's name is also format- and path-dependent: a JSON/ndjson envelope carries `artifact_path`, the TEXT envelope renders the same value as `path:`, and a spilled MUTATION carries neither on stdout — it prints the compact status plus `detail_artifact_path` (a status is not an envelope, so it has no `spilled` field at all). The safe gate per shape: `.artifact_path` on a JSON/ndjson read, `path:` on a text read, `detail_artifact_path` on a mutation. A piped spill also prints a stderr `warning:` + pipe-caution. Inside `summary`, `count` is the on-disk **page** size and `total` the logical total. **`.total` is hoisted only when the payload has one**: JSON read envelopes hoist `summary.total` to the top level (paged and spilled alike, so `.total` survives a spill), but it is absent from the text envelope, `null` on a fan-out aggregate, and scoped under the ndjson metadata object rather than hoisted.
  - **`taint forward` per-sink JSON is nested (#311):** each reached sink is `reached_sinks[].sink.{class, callee, address, detail, tainted_arg_index}` plus `reached_sinks[].path[]` — so use `jq '.reached_sinks[].sink.class'` (**not** `.reached_sinks[].class`, which is null). `taint backward`: slices are `slices[].sink.{kind, callee, address, seed}` + `slices[].origin` + `slices[].slice[]`; **every** sink's status is in `sink_status[]` — `.seeded: true` (with `.slices` count) = sliced, **`.bounded: true`** = a provably-bounded constant length (a success, exit 0), and `.seeded: false` *without* `.bounded` = genuinely couldn't seed.
  - **Nothing-found vs incomplete (don't confuse them):** `items: []` + `total: 0` means *clean — nothing found* **only when the payload carries no cap flag**. A capped read can be empty and incomplete at once: an `xrefs` page whose import caller scan stopped at its budget comes back `items: []` with `truncated: true` and a `scan_note`, which is *unknown*, not absence — text mode says so with a `note: the caller scan was TRUNCATED` line. A `virtual_call` read is capped on two independent axes as well: a slot beyond a provider's recovered **vtable window**, and the provider-**class** sweep budget — a sweep cut short reports `classes_truncated: true` with `classes_scanned`/`classes_total`, and the caveat lands in `warnings` when a candidate was found inside the scanned prefix (so `resolved: true` is not a whole-provider answer) or in `unresolved_reason` when no candidate was found. `has_more: true` means *more pages exist* (paging). For **taint**, the `leaves` (frontiers) are the "couldn't follow further" signal — a non-empty `leaves` (or `truncated: true`) means incomplete, NOT an all-clear; the text output's `verdict:` line says "NOT an all-clear" explicitly. `assumptions` are caveats (how a source/sink was anchored, value-set/agent-map resolution sets, broad-source over-tainting, depth truncation), not a re-list of frontiers. For **trace** and **`evidence message`**, a non-empty `assumptions` array means *the analysis hit a cap and is incomplete* — NOT an all-clear.
  - **Project-internal wrappers — model them so taint follows them (#317).** When a taint flow stops at an `unmodeled_callee` frontier for one of the *target's own* copy/format/exec wrappers (a non-libc name like `app_copy`/`shell_run` the builtin model DB can't know), declare it with `taint forward/backward --models <file.json>`: a JSON map `{"app_copy": {"sink": {"class": "overflow_len", "tainted_args": [1]}, "propagates": [{"from": "*arg:1", "to": "*arg:0"}]}}` in the same schema as the builtin DB, merged over the builtins (user entries win a name clash). A malformed file is a loud error, not a silent skip. To persist the same models across every invocation instead of per-command, point `BN_TAINT_MODELS` at the file -- `--models` wins when both are set for one invocation. A malformed `BN_TAINT_MODELS`-referenced file is loud (same as `--models`); a *missing* one is silently ignored, matching the bridge's own spawn-time handling of the same variable.
    - **Bounded-WRITE sinks — wrapped `recv(len)`/`read(len)` overflows (#443).** A length-prefixed-protocol overflow — a wrapper that forwards an attacker-controlled length straight into `recv`/`read` writing into an undersized buffer — is neither a copy sink (`arg:memcpy:N` doesn't apply) nor caught by the `recv`-as-source model. Declare the wrapper a **bounded-write sink** with `len_arg` (the attacker-controlled write length that arms the sink) and `buf_arg` (the destination, for the provably-bounded downgrade): `{"app_recv": {"sink": {"class": "overflow_len", "len_arg": 1, "buf_arg": 2}}}` for `app_recv(fd, len, buf)`. Then `bn taint forward --function <handler> --source call:recv --models <file>` flags the wrapped `recv(len)`-into-undersized-buffer as `overflow_len`, and a buffer allocated to the same length (`buf = malloc(len)`) is downgraded to `bounded_len`. Model the raw `recv`/`read`/`recvfrom` the same way (`len_arg: 2, buf_arg: 1`) when auditing a target that recvs attacker lengths directly. (A `calloc(1, len)`-sized buffer currently stays `overflow_len` — a safe over-report, since `_dest_alloc` doesn't yet model `calloc`'s two-arg size.)
    - **Unconditional (always-unsafe) sinks — no `tainted_args`, no `len_arg`.** A sink with neither armed field (e.g. the builtin `gets` model) fires on every call, independent of `--source`, and injects taint into its own destination buffer for downstream sinks to pick up. That destination is `sink.buf_arg` when declared; otherwise the engine falls back to the model's own `sources[]` entries, picking the **first** one whose `to` is `*arg:N` (declaration order in the JSON, not argument-index order). A model with more than one `*arg:N` source and no explicit `buf_arg` therefore has its injection point picked by entry order, not by inspection — declare `sink.buf_arg` explicitly whenever a model has multiple buffer-typed `sources[]` entries to pin the real destination instead of relying on it.
- **JSON list-command field map (the `.items[]` idiom and its exceptions).** Most list/search read commands share one paged envelope — `{kind, items, total, offset, limit, returned, has_more}` — so `jq '.items[]...'` is the near-universal extractor (`strings`, `imports`, `exports`, `sections`, `types`, `function list`/`search`, `callsites`, `xrefs`, `comment list`, `class list`, and the admin/runtime listings `target list`, `session list`, `instance list` — the last three carry `kind` + `items` plus their own extras like `total_rss_mb`, see #358). The catch: the *leaf* field holding the payload is **not always named after the command**, and selecting a wrong/missing key yields `null` (a wall of which reads like "no results"), never an error. Per-command leaves:
  - `strings` → `.items[].value` (the string text — **not** `.string`)
  - `types` → `.items[].decl` (the C declaration text) + `.items[].layout`, alongside `.name`/`.kind` (**not** `.definition`/`.type`). Aggregate types also carry a structured `.items[].members[]` (`{name, offset, type}`), with an anonymous nested union/struct expanded into a nested `members[]` so its inner fields aren't invisible (#370)
  - `comment list` → `.items[].comment` (**not** `.text`); each item also carries `.address` and `.function`
  - `callsites` → the payload is **nested**, with no flat `.name`/`.address`: use `.items[].caller_static`, `.items[].callee.name`, `.items[].containing_function.name`
  - `function list`/`search`, `imports`, `exports` → `.items[].name` + `.items[].address` (plus `raw_name`/`display_name`, and `kind` on imports/exports)
  - `class list` → `.items[].name`, `.method_count`, `.has_vtable`, `.size`, `.bases`, `.confidence`
  - `sections` → `.items[].name` + `.start`/`.end` (hex strings) + `.length`, `.semantics` (e.g. `ReadOnlyCode`), and segment-derived `.readable`/`.writable`/`.executable` (present **only when the section has a backing segment** — absent, i.e. `null` under `jq`, otherwise)
  - `xrefs` → `.items[]`, each row carrying `.kind` (`code` | `data`), `.function` (containing-function name), and `.caller_function.{address,name}`. Filter by kind with `jq '.items[] | select(.kind=="code")'`; full-set totals are `.code_ref_count` / `.data_ref_count`. (Pre-#184 the op exposed top-level `code_refs`/`data_refs` arrays; those were dropped — `jq '.code_refs[]'` now returns empty and misreads as "no refs". The dual `code_refs`/`data_refs` shape survives only in `function info` / evidence embedding, not the `xrefs` command.) For per-ref attribution prefer **`.caller_function`**: it is computed per reference, whereas `.context.function` is the *primary* containing function at that address (computed once per address). When two BN functions **overlap** the same address, the duplicate rows correctly carry different `.caller_function` but share an identical `.context.function` — `caller_function` is authoritative for which function each ref belongs to (#364).
  - `local list` → `.items[].name`, `.type`, `.storage`, `.index`, `.is_parameter`, and **`.local_id`** — a stable handle; prefer it over names, which drift across re-analysis. Its envelope is `{function, kind: "locals", items, locals}`: `locals` is a **retained alias** for the same list (it was the only container before #651, and `jq '.items[]'` returned null against it — which reads like "this function has no recovered variables"). Prefer `.items[]`.
  - `comment list` items also carry **`.scope`** — `address` for an address comment, `function_doc` for a function documentation comment (`fn.comment`, written by `comment set --function`). Both stores are listed by default; `--scope address|function` narrows. `--query` searches both, so a `TODO:` marker in a function doc is findable (before #643 it was not: the write reported `verified` and `comment list --query TODO` reported `none`).
  - **Addresses in JSON are hex STRINGS**, not integers: `{"address": "0x401ed8"}`. Any arithmetic needs `int(x, 16)` / `tonumber` on the parsed value — this is consistent across every command, but it costs one traceback to discover. Same for `start`/`end` on sections and `entry_address` on table rows.
- **`evidence function` / `callsites` argument + statement fields — read the confidence, not just the value.**
  - `argument_confidence` is `authoritative` only when HLIL produced the list **and** the callee's arity is known without a count mismatch. When the callee has no recovered prototype, BN assumes every ABI argument register is live and HLIL renders whatever happens to sit in them — typically the *neighbouring* call's argument staging, up to and including `__stack_chk_guard`. Those calls report `argument_confidence: "inferred"` with **`arity_unknown: true`** (plus `abi_register_saturated: true` when the count saturates the ABI argument registers, the strongest tell), so you can filter them (#648). A bundled or user prototype establishes the expected arity, not the accuracy of the rendered list: extra or missing HLIL arguments demote it to `inferred` with `arity_unknown: false` (#742). A *matching* count is not sufficient on its own either, because both numbers can come from the same under-recovered prototype: when an attached type library contradicts the callee's recovered prototype the row is demoted with `prototype_unverified: true` (below). A user-declared zero-parameter prototype is a known count too. Variadic prototypes are not checked for an exact count.
  - Three more signals from the same demotion logic: `arity_mismatch: true` when a resolved, non-variadic callee's declared parameter count does not match the rendered argument count in either direction (extra OR missing arguments, alongside a `declared_arity` int) — the flag only fires on an **available, HLIL-sourced** argument list (`argument_source: "hlil"`), including a genuine zero-argument list. An unavailable HLIL list falls back to MLIL/LLIL with `heuristic` confidence; it never masquerades as a zero-argument HLIL call or sets a mismatch (#704, #742). The other signal is `callee_unresolved: true` when the call's destination could not be matched to any callee function at all; these calls remain `heuristic` (distinct from `indirect_call`, which only means the destination itself was not a resolvable constant — set ONLY when true, like `abi_register_saturated`, so a direct call to an unmatched address is `indirect_call` **absent** / `callee_unresolved: true`). The third is `prototype_unverified: true`, when an attached type library declares a different parameter count than the callee's recovered prototype -- an INDEPENDENT witness, since the library signature is not derived from this binary's analysis, so unlike `arity_mismatch` it can catch a callee whose prototype and rendered list agree with each other because both are under-recovered. The `evidence function` row carries `declared_arity`, `library_arity` and `library_source` (the library that supplied the count), and its text card states an `arity: UNVERIFIED` line; `callsites` rows carry no arity fields at all, so none of this appears there. It is deliberately narrow, and the narrowing is what keeps it from crying wolf. A **decorated** name is refused outright, whatever its provenance, because implicit `this`/sret parameters make a count comparison meaningless: that means the mangling prefixes which are themselves valid C identifiers (`_Z` Itanium and Rust-legacy, `_R` Rust v0, `_D`, `_T` older Swift) as well as the spellings an identifier rule already excludes (MSVC `?name@@...`, current Swift `$s...`, GCC clone suffixes like `f.part.0`, versioned symbols like `memcpy@GLIBC_2.14`). Of the ordinary C identifiers that remain, the library is taken to describe the callee only when it is an **import**, or when its name is in the implementation's reserved namespace (a leading `__`, which a conforming program cannot define, so a statically linked copy is still the library's function). Beyond that: libraries that disagree with each other settle nothing, and a variadic library signature makes no claim. A **user prototype is not exempt**, and that is deliberate: BN sets `has_user_type` on almost every function and exposes no API to clear it, so after a save and reopen it reads true for essentially everything -- suppressing the check for it disabled the whole cross-check on every saved database. A prototype you pinned yourself can therefore be flagged, and the disagreement is one reason that row is not fully corroborated rather than the whole story -- a co-occurring `arity_mismatch` or `arity_unknown` prints its own reason line, and an MLIL/LLIL-sourced list is `heuristic` whatever the library says. The row names both counts and the library, and the text card says plainly that it may be disagreeing with your own statement. Confirm with `bn proto get` and decide which is right for this binary: the check cannot tell a prototype you pinned from one BN recovered. Three shapes are therefore still reported `authoritative` even when their arguments are under-recovered, and they are the real blind spots rather than just the obvious one: a callee **no attached library names**; a callee with a **decorated name** (`_Z`/`_R`/`_D`/`_T`, MSVC, Swift), which a library may well name but whose implicit `this`/sret parameters make a count comparison meaningless; and an **ordinary-named library function linked statically**, which is named by a library but is neither an import nor `__`-reserved, so nothing establishes that the signature describes it rather than a same-named function of the program's own. All three are tracked in #865, whose scope was widened from its original no-library-entry filing to cover the two library-named shapes as well -- they are one gap, not three: nothing independent of this binary's own analysis can settle the arity. The `mlil:` line and its `argument_candidates` source the LLIL instruction's TRUE per-instruction MLIL (`insn.mlil`), not the caller-register-coalesced mapped form — it shows the callee's actual operands, not the caller's ABI registers (#661).
  - `hlil_statement` resolves for a call whose **return value is discarded** — a bare `memcpy(...)`/`free(...)` statement, the most common shape in real code. It used to be `null` with reason `no_local_statement` for every one of them (0 of 387 callsites on one target), because such a call's HLIL parent is the enclosing block rather than an assignment (#644). When it *is* null, `hlil_statement_reason` says why: `no_hlil_mapping`, `hlil_not_call_shaped`, `ambiguous_fold`, `statement_not_local`, `no_local_statement`.
- **aarch64 decompiles carry dead `int128_t vN_M` declarations.** Each call site is preceded by ~8 `int128_t v0_6; … int128_t v7_6;` — the AArch64 `v0`–`v7` variadic-register phantoms — which are then re-passed into the call. This is upstream BN rendering, not a `bn` artifact, and on one target it roughly **tripled** decompile artifact size. Expect it, and pipe through `grep -vE 'int128_t v[0-9]'` when the volume matters.
- `bn evidence ...` is a read-locked family that surfaces the **raw material** behind a call/table/type so you don't have to hand-roll `py exec` — built for stripped C++/firmware. `evidence function <fn>` pairs each call's raw disasm with LLIL/MLIL/HLIL argument evidence and flags thunks (including PLT/import trampolines); `evidence xrefs` annotates each ref with section/segment/symbol + the referencing disassembly; `evidence table <addr>` reads a pointer/vtable table, is **ARM/Thumb-aware** (clears the T bit and resolves the even entry, marked `[thumb-adjusted]`), and tags each slot with a row-level `status` (`function`/`mapped`/`null`/`unmapped`, or `unreadable` when the slot bytes can't be read) + `plausible` plus low-confidence `warnings` when the address doesn't look like a table; for a **mixed-record** dispatch descriptor (scalar fields interleaved with pointers, common in firmware), `--record-size N --ptr-fields o1,o2` scans records of `N` bytes and classifies only the declared pointer offsets (`kind: record_table`, one `{row, base, fields}` per record) so an inline opcode/flags scalar isn't rendered as a noisy failed pointer slot (#455); `evidence message <type-string>` is a protobuf/RTTI lens (type-name → xrefs → nearby metadata windows, e.g. the serializer slot); `evidence init` summarizes `.init_array`/`.ctors` constructor pointers; `evidence virtual-call` resolves a requested slot even when it sits PAST another command's 64-slot display window (it reads just that slot from the provider, re-checking the rows in between, while the listing stays capped), and types every non-resolution in `unresolved_reason_code` beside the prose `unresolved_reason`: `slot_not_present` (every provider table that was READ genuinely ends before the index -- the only absence claim), `vtable_scan_truncated` (a scan stopped before the index -- capped, or stopped at an entry it could not read -- so the slot is unknown, never absent; for a resolved set, `warnings` says another provider was not fully scanned), `vtable_body_unresolved` (a provider class had no vtable this command could READ -- defined in another module, applied at load time, its symbol absent, or the read failed -- so the slot was not searched there; `warnings` says so beside a resolved set), `slot_present_no_method` (an entry sits at the index but holds no callable target: a null/pure-virtual placeholder, the next object's padding, or a cross-module entry), `vtable_slot_probe_limit` (the requested index is further past the window than the targeted read will walk) and `slot_offset_not_aligned` (#531). Large results spill to disk like other read ops.
- **`bn evidence surface`** enumerates the **hidden code surface** a passive `bn function list` misses — code reachable through **data**, not direct calls (#503). One read-locked digest composing: **init/ctor sections** (pre-main constructors, each flagged whether BN recovered a function); **candidate vtable/dispatch tables** (runs of ≥`--table-min-run` consecutive pointers-into-executable, with resolved-vs-missing slot counts — scanning named data sections `.data`/`.rodata`/`.data.rel.ro` when present, else falling back to the readable **segments** so it works on a raw/monolithic firmware image with no named sections, e.g. a VxWorks kernel loaded as one r-x region; those tables usually sit in the image **tail**, so raise `--max-scan-bytes` if the cap warning fires); and **missing-function candidates** — the deduped executable targets with **no BN function**, each carrying `aligned` and **`decode_depth`** (the count of sequential valid, non-undefined instructions from the target) plus a **`code_likely`** flag (aligned + a long clean run). Decode depth is the real code-vs-data discriminator on fixed-width RISC firmware: measured on aarch64, known functions decode a long clean run (median ~24) while data hits an undefined instruction almost immediately (median 0) — a single decode is useless (~90% of data decodes to one instruction). Start with the `code_likely` subset (default `decode_depth ≥ 8`, ~2% false-negative on real functions), then **confirm with `disasm`**; the raw depth is reported so you can tighten/loosen. (Weaker on dense x86, where data rarely hits an undefined — there lean on `aligned` + the table's resolved/missing ratio.) It is **read-only** — it reports the addresses BN missed but does **not** create functions (`function create` is the agent's next, separate step, and only for the ones you confirm with `disasm`). On a fully-analyzed clean binary it typically shows the init/vtable structure with `missing=0`; the value is on stripped/optimized firmware where BN's linear sweep didn't reach code that only a runtime dispatch table references. Caps (`--max-tables`/`--max-candidates`/`--max-scan-bytes`) are disclosed in `warnings` when hit, never silently truncated — and the warning names the **pre-cap total** (`capped at 128 of 514`), also carried as `summary.missing_function_candidates_total` / `candidate_tables_total`, so you can judge whether raising the cap is worth it (#653).
  - **"Pointers-to-code" means the target's SECTION is code, not merely that its segment is `r-x`** (#647). On a single-`LOAD` aarch64 PIE the whole image — `.rodata` included — is mapped `r-x`, and a segment-permission test therefore accepted every pointer into read-only *data*: a 514-row `{char *desc; char *usage;}` help table was reported as a 514-entry dispatch table with 514 "missing functions", 127 of which were string bodies. The scan now requires BN's section semantics to be code-like (`.text`/`ReadOnlyCode`), and a candidate that resolves to a printable string carries it inline (`-> "Set Channel Index"`) so a false lead is self-refuting. A view with **no** sections (raw/monolithic firmware) keeps the permissive behaviour, so the scan is not blinded on its primary target class.
- **`evidence calls <reg-fn> --arg-struct N --field …`** recovers the values a **transient stack descriptor** carries into a registration/ops-table API, at every callsite — the manual "decompile each caller and scrape the stores into the stack struct before the call" workflow, done in one command (#469). Declare the layout with repeatable `--field NAME:TYPE@OFF` (TYPE = `u8/i8/…/u64/i64`, `char[N]`, or `ptr` — a `ptr` field resolves the pointed-to function/data **symbol**, so callbacks come back named). `--arg-struct N` is the 0-based call argument that is the `&descriptor`. It works whether the compiler kept the struct as one typed local or (stripped/optimized) split it across sibling stack slots — fields are matched by **descriptor offset**, not by a single variable. Unknown fields (never written) and non-constant/merged fields are marked explicitly (`<unknown>` / `<computed>`), never silently dropped; JSON carries `caller`, `call_address`, and per-field `status`/`value`/`symbol`/`source_address` (the instruction that wrote the field). **Best-effort caveats:** each field is the last write **by instruction address** before the call, so a value set only on a not-taken branch (or across a loop) can be attributed when a full path analysis wouldn't — the `source_address` lets you confirm at `bn decompile`; and sibling-slot recovery matches a stack slot at `base + declared-offset`, so declaring an offset that lands on an unrelated adjacent local could mis-attribute it. Declare only offsets you know are descriptor fields. Sanitized example — a command dispatcher registered via `init_cmd(dev, &desc)`:

  ```c
  struct CmdDesc { uint16_t command; uint8_t type; uint8_t subtype; uint8_t flags;
                   uint16_t expected_len; void *context; void (*callback)(void*, uint8_t*, uint16_t); };
  void send_status_cmd(Device *d) {
      struct CmdDesc desc = {0};
      desc.type = 0xed; desc.subtype = 0x41; desc.flags = 0x27; desc.callback = status_rsp;
      init_cmd(d, &desc);
  }
  ```

  ```bash
  bn evidence calls init_cmd --arg-struct 1 \
     --field command:u16@0 --field type:u8@2 --field subtype:u8@3 \
     --field flags:u8@4 --field expected_len:u16@6 --field callback:ptr@16
  # caller=send_status_cmd call=0x402150 command=0x1101 type=0xed subtype=0x41 flags=0x27 ... callback=0x401139 (status_rsp)
  ```
- `bn trace <fn> <addr> [--arg N] [--interprocedural]` walks **MLIL SSA use-def chains backward** from a call-site argument to trace where it originates. It shows each intermediate SSA variable with its defining instruction and address, terminating at a function parameter, global, memory load, or call boundary. A value that bottoms out at a local whose address was passed into an earlier call in the same function is reported as `out_param_not_followed` (or `interprocedural_out_param_not_followed` under `--interprocedural`), naming the filling callee, rather than the misleading `undefined_or_global`. Add `--interprocedural` (with `--ip-depth N`, default 2) to follow **return values** across call boundaries into callee functions when the callee has a real MLIL body — this works best for self-contained code (static binaries, kernel modules). IP mode follows a value into a callee only when it is that callee's return value, and stops at the callee's own parameters (it does not map callee params back to caller args, nor walk up the caller chain — step up with `bn xrefs` + re-run for those). **Out-pointer / output-parameter writes are not followed**: when a value is loaded from a local that an earlier call filled by-address (`parse(input, &out); use(out.len)`), the slice reports `interprocedural_out_param_not_followed` and names the callee that received the out-pointer, rather than tracing into the callee or silently bottoming out at the local — so the stop is not mistaken for proof of origin (#416). For dynamically-linked PLT/import calls, `--interprocedural` correctly falls through (no callee body to enter), producing identical output to intraprocedural mode. JSON output includes `interprocedural` and `ip_depth` fields. Example:
  ```bash
  bn trace main 0x27e1a --arg 1                              # intra: stops at call boundary
  bn trace main 0x27e1a --arg 1 --interprocedural            # IP: follows into callee if possible
  bn trace handle_l2cap_con_req 0x1c2bc --arg 2 --format json # structured JSON output
  ```
- `bn read --address <addr> --length <N>` returns raw bytes from the mapped view — the parallel-safe alternative to a `py exec` `bv.read(...)` (it runs under the shared read lock). Text mode prints an offset/hex/ASCII hexdump; JSON returns `{address, length, hex, ascii}`. Two ways a read comes back **partial**, each with `requested_length` and a `note` and neither an error: a window that runs past mapped memory comes back short (`short_read: true`), and a `--length` above the hard ceiling of **100000 bytes** is served truncated at the ceiling (`capped: true`) — ask for a larger region in successive windows. An entirely unmapped address *does* error (`Address 0x... is not mapped`). Add `--encoding bytes` to stream the raw bytes to stdout (or to `--out <path>`) instead of a hexdump — useful for piping a blob into another tool or saving it to disk. In that mode stdout carries only the payload, so either partial marker is reported as a `note:` line on **stderr** (and in the `--out` summary alongside `requested_length`); redirect stdout, not stderr, when piping.
- `bn function create <address> [--preview]` forces Binary Ninja to create and analyze a function at `<address>` when auto-analysis missed it. **When to reach for it:** a code entry point that BN never disassembled because it is reachable only through a **data pointer** (a vtable slot, a function-pointer table, a handler/dispatch array) and has no direct `call`. Point `bn read` / `bn xrefs` at the pointer table to recover the target address, then `bn function create` it so `decompile` / `xrefs` / `callsites` work on it. It is a verified mutation, so it honors the same `--preview` (create → verify → revert) and live-verify loop as the other mutations: it returns `noop` if a function already starts there, errors if the address is unmapped or not inside an executable segment, and rolls back with `verification_failed` if analysis produces no function. Save afterward (§6 step 4) to persist the new function.
- `bn function cfg <fn> [--view asm|mlil|hlil]` returns the function's **basic-block graph** — blocks, their instructions, and the typed edges between them. `structured_il` returns a flat instruction list with no block partitioning, so reach for `cfg` when the question is about control flow itself: which block dominates which, where a loop back-edge lands, whether a branch is conditional. Each block carries `insns` (`a` = address, `t` = text) and `edges` (`to` = destination, `k` = edge kind).

  **Index contract — read this before using `to`.** At `--view asm` a block's `to` values are **addresses**. At `--view mlil` / `--view hlil` they are **IL instruction indexes**, while each instruction's own `a` remains the real address. Do not feed an IL-level `to` into an address-taking command; resolve it through the block's own instructions first.

- `bn data vars --start <addr> --end <addr>` lists the **typed data variables** in an address window: `a` (address), `n` (name), `t` (type), `w` (width), `v` (value), `p`/`ps`/`pstr` (pointer target, its symbol, and the string it resolves to, when the var is a pointer), `sec` (section). The window is **mandatory** — this is a windowed read, not a whole-binary dump. Use it to walk a struct table or pointer array after `bn evidence table` has located one.

- `bn data symbols` lists every **named DataSymbol** as `a` + `n`, including internal symbols that `bn exports` omits — so a data global you renamed stays addressable by name. Paged like the other list reads (`items` + `total`/`offset`/`limit`/`returned`/`has_more`).

  All three dispatch under the **shared read lock**, so they stay responsive while another client holds the view. That is the point of them: the same reads through `py exec` take the exclusive **write** lock (arbitrary Python can mutate the view, so it must), and because the lock is writer-preferring, one queued `py exec` stalls every other client's reads. Prefer these over hand-rolled `py exec` equivalents.

## 5. Caller-static mapping

Prefer `bn callsites` over ad-hoc `py exec` whenever the task is "find the exact native return-address callers" or any direct-call mapping workflow.

`bn callsites` reports:

- `call_addr` — the native `call ...` instruction address.
- `caller_static` — the post-call return address (`call_addr + instruction_length`).
- `call_index` within the containing function, `within_query`, previous/next instructions, a local-or-null `hlil_statement`, and a best-effort `pre_branch_condition`.

```bash
bn callsites crt_rand --within bonus_pick_random_type --caller-static
bn callsites crt_rand --within fx_queue_add_random   --caller-static
bn callsites crt_rand --within-file /tmp/rng-functions.txt --format json
```

`--within-file` accepts one identifier (name or hex address) per non-empty line; lines beginning with `#` are ignored.

`hlil_statement` is intentionally local-or-null — when Binary Ninja only exposes a coarse enclosing region, expect `null` instead of a noisy whole-function blob. `pre_branch_condition` is the nearest enclosing pre-call HLIL condition when it can be recovered confidently; `null` is normal.

The row set is unioned from the LLIL destination **and** the code-ref DB (what `xrefs` reads), so a call the xrefs/dataflow evidence confirms is never dropped for want of a matching LLIL operand. A call whose address the function's structured disassembly walk never decoded keeps its row with its identity fields (`call_addr`, `callee`, `containing_function`, `caller_static`) intact, a `null` `call_instruction` with empty `previous_instructions`/`next_instructions`, and `disasm_context_reason: "no_structured_disasm_entry"` saying why the context is missing — so a hole is never mistaken for "not called". Caller **enumeration** closes the same gap: for an imported callee BN recorded no code ref for, the caller set comes from the same bounded LLIL call scan `xrefs` uses (#622), so `callsites` never reports fewer sites than `xrefs` for the same callee. A scan that hits its budget, or LLIL it could not read, is disclosed rather than reported as a count: `caller_scan_truncated: true` with `caller_scan_note` naming which happened, `total: null` plus `total_lower_bound`, `caller_total: null` (how many callers exist is what the capped scan was still deciding — `callers_scanned` still reports how many it examined), and text mode printing the reason — an incomplete caller list never reads as "not called".

**High-fan-in `total` is monotone, not missing.** A callsites read stops scanning callers once it has enough rows for the requested page, so a high-fan-in callee's page reports `total: null` plus `total_lower_bound`, `scan_truncated: true`, `callers_scanned` and `caller_total` — "at least N, exact count not computed to keep the scan bounded", never zero. A page whose scan *did* cover every caller reports the exact integer `total`. Across the pages of one collection that refines in one direction only: `null` → integer is normal (and is how a large `callsites` collection ends), while an already-determined integer never reverts to `null` and never changes — the client page validators (`bn.Client.collect`, the bn-kernel `Session` collectors) reject those as bridge drift (#694).

If you call `bn callsites <callee>` without `--within` / `--within-file`, the CLI prints a 3-option help block (`single caller`, `many callers`, `list callers`) instead of erroring.
